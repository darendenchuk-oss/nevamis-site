# Homepage blocking time, 2026-09-12

The owner's directive was "speed up the whole website ... make the website fast
and responsive", against a client-side audit that put the marketing homepage at
roughly 5,400 ms of total blocking time on load and `/pricing.html` at 13 ms,
and attributed the difference to the film.

This is what was measured, what was changed, what was measured again, and what
was measured and deliberately not shipped.

## How these numbers were taken

Playwright's bundled Chromium (1.63.0, Chrome Headless Shell 153), one page load
per run, CPU throttling 4x via `Emulation.setCPUThrottlingRate`, a mobile profile
(412x823 at device pixel ratio 1.75, mobile user agent, touch), ten seconds of
observation after the load event. Pages were served by `node serve.js` from this
worktree, which gzips text the way GitHub Pages does. The baseline was served
from a second, untouched worktree at `8e1d184` on its own port, so baseline and
change were measured on the same machine, in the same window, minutes apart.

Recorded per run: every `longtask` entry with its duration, the largest
contentful paint, the paint entries, the navigation timings, a CPU profile
sampled at 200 us (self time attributed by script URL, and each long task
attributed to the script with the most self time inside its window), and the
timestamp of the first WebGL draw call plus the number of draw calls in the
window, from a hook on `WebGLRenderingContext.prototype.drawElements` and
friends.

Two blocking-time figures are reported because they answer different questions:

- **TBT from navigation start**: every long task's duration over 50 ms, summed,
  from the moment navigation began. This is the one to compare across a change,
  because it does not move when first paint moves.
- **TBT from first paint**: the Lighthouse definition. It is reported for
  completeness and it is misleading on its own here: work that happens before
  first paint is not counted, so a change that makes the page paint sooner can
  raise this number while making the page strictly better.

**This machine is shared and noisy.** Run to run on identical code, the same
page varied by 25 per cent, and during one window the untouched control page went
from 470 ms to 20,331 ms of blocking time because other work was running. Every
figure below is the least contended of three runs, and `/pricing.html`, which
this branch does not touch, is reported beside every pair as the proof that the
two sides are comparable. Where a difference sits inside the spread, it is called
that and not called an improvement.

## Before

Baseline `8e1d184`, homepage, motion enabled:

| | value |
| --- | --- |
| TBT from navigation start | 7,224 ms |
| TBT from first paint | 5,601 ms |
| First contentful paint | 1,188 ms (best of three; 1,188 / 2,624 / 2,660) |
| Largest contentful paint | same element and time as FCP |
| Long tasks over 50 ms | 34 |
| Longest single task | 858 ms |
| WebGL draw calls in ten seconds | 1,329 |
| First WebGL draw | 198 ms |

Main-thread self time in that run, by script: `(program)` 6,883 ms (time inside
the GL driver, not in any script), `film-1.js` 954 ms, `film-2.js` 669 ms,
`film-3.js` 185 ms, `site.js` 34 ms.

`/pricing.html`, the control, on the same machine in the same window: 433 ms of
blocking time, first contentful paint 772 ms, 4 long tasks, longest 388 ms. The
audit's 13 ms figure came from a different harness; the ratio is what matters,
and it was seventeen to one.

Where the homepage's time went:

1. **A 858 ms task at 107 ms**, attributed to `film-2.js` and `film-1.js`: the
   three.js bundle parsing and the film building its scene. This is parser
   blocking and it is in front of first paint.
2. **A 798 ms task at 1,008 ms**, 94 per cent of it inside the GL driver: the
   first composed frame. three compiles a material's program the first time it
   draws that object, so the film's entire shader set is built here.
3. **Thirty more tasks of 200 to 660 ms, out to ten seconds.** This is the
   ignition, and it should have taken 1.9 seconds. It integrated the frame's
   `dt`, which is clamped to 50 ms so that one slow frame cannot throw the
   camera; on a machine composing a frame every 230 ms that clamp advanced the
   ignition at a fifth of real time, so 1.9 authored seconds became roughly
   seventeen, and `IW.on` holds `needMore()` true for every one of them. 1,329
   draw calls in ten seconds is that.
4. **Off the clock but on the page**: the scroll handler called
   `requestRender()` for every scroll event whether or not the film was on
   screen. `#stage` is sticky inside a ten-viewport `#scroll`, so reading the
   sections below the film re-composed the whole scene, bloom and grain
   included, behind them.

Reduced motion, baseline: 1,531 ms of blocking time, first contentful paint
1,292 ms, 3 long tasks, longest 993 ms, 87 draw calls. There is no loop in that
mode and never was; the cost is building a scene in order to draw it once, and
composing that one frame in front of the page's own paint.

Production, `https://nevamis.ca/`, same harness, two runs: 8,087 ms of blocking
time, 41 long tasks, longest 1,831 ms, 1,503 draw calls, first contentful paint
580 ms. Production paints sooner than the local server does, because the film
scripts arrive over the network after the header has already painted, and then
the page is unresponsive for about eight seconds. **On production the homepage's
problem is not the paint. It is the eight seconds after it.**

Same machine, same window, three commits on `perf/homepage-blocking-time`:

| --- | --- | --- | --- |
| TBT from navigation start | 7,224 ms | 3,083 ms | **-57%** |
| TBT from first paint | 5,601 ms | 2,281 ms | -59% |
| First contentful paint | 1,188 ms | 1,096 ms | inside the spread |
| Largest contentful paint | 1,188 ms | 1,096 ms | inside the spread |
| Long tasks over 50 ms | 34 | 9 | **-74%** |
| Longest single task | 858 ms | 1,027 ms | +169 ms |
| WebGL draw calls in ten seconds | 1,329 | 319 | **-76%** |

| homepage, prefers-reduced-motion: reduce | before | after | change |
| --- | --- | --- | --- |
| TBT from navigation start | 1,531 ms | 966 ms | **-37%** |
| First contentful paint | 1,292 ms | 1,268 ms | inside the spread |
| Long tasks over 50 ms | 3 | 2 | -1 |
| Longest single task | 993 ms | 744 ms | -249 ms |
| WebGL draw calls in ten seconds | 87 | 48 | -45% |

| /pricing.html, control, not touched | before | after |
| --- | --- | --- |
| TBT from navigation start | 433 ms | 436 ms |
| First contentful paint | 772 ms | 692 ms |
| Long tasks over 50 ms | 4 | 3 |

The control moving by 3 ms is what makes the homepage's 4,141 ms real.

Blocking time, task counts and draw calls are from the least contended run of
three, chosen by blocking time. First contentful paint is reported as the lowest
of the same three runs rather than the paint from that one run, because it is the
most contention-sensitive number here and the lowest is the closest to an
uncontended machine: before 1,188 / 2,624 / 2,660 ms, after 1,096 / 1,264 /
2,636 ms. On that reading the paint did not move, and it was not expected to:
building the scene is still parser-blocking, and it is the paint's floor.

One thing did change in the picture, in reduced motion only, and it is a fix
rather than a regression. The still frame is composed after a `layout()` call
that now always sees a laid-out canvas. Where the canvas was already laid out at
construction, the extra call returns early and the frame is byte-identical; where
it was not, the old code composed at the renderer's un-laid-out size and the hero
strip came out blank. The local server reproduces the second case every time: on
the baseline the reduced-motion hero is an empty dark panel, and on this branch
it is the film. Production, whose network latency happens to let layout run
first, renders the still correctly today and is the "already laid out" case.

Main-thread self time after, by script: `(program)` 2,090 ms (was 6,883),
`film-1.js` 685 ms, `film-2.js` 454 ms, `site.js` 152 ms. Idle time in the
ten-second window went from 3,192 ms to 8,244 ms, which is the same fact said
the other way round: the page now spends most of that window doing nothing.

### What changed

1. **The first composed frame waits for the page.** It now runs after the load
   event, after a first contentful paint the browser has actually reported,
   after two frames and an idle callback with a timeout. Waiting on load alone
   was tried and measured and is not enough: on a throttled machine load fired
   about 250 ms after parsing finished, the browser had not painted yet, and the
   film's frame went in front of the paint anyway (first contentful paint
   2,964 ms, no better than before). Until the frame arrives, `#stage` carries
   the same radial ground that no-WebGL visitors already get, behind the same
   canvas at the same inset, so nothing moves. `nv-late` keeps the ignition's
   cold-open from blinking the header and the scroll hint, which are on screen
   before the film now.

2. **Nothing off screen is drawn.** An `IntersectionObserver` on `#stage` stops
   the loop when the film scrolls out of view and restarts it on return,
   snapping `cur` to the scroll position rather than lerping to it. The
   hidden-tab rule already existed; this is the same rule for the part of the
   page you have scrolled past.

3. **The ignition lasts its authored 1.9 seconds on every machine.** It reads
   real elapsed time instead of the 50 ms-clamped physics `dt`, with its own
   ceiling for a tab restore. This is the single largest contributor to the draw
   call and long task counts above.

4. **Reduced motion gets its words before its picture.** The three copy blocks
   are revealed immediately and the one still frame is composed on the same gate
   the loop uses.

## Measured and not shipped

**Deferring the film's construction, not just its first frame.** This is the
change the directive asked for first, and it is the biggest single win available:
loading `film-1.js`, `film-2.js` and `film-3.js` after load and idle instead of
on the parser took first contentful paint from 2,972 ms to 692 ms and the load
event from 3,357 ms to 688 ms on the harness used at the time.

It also changes what the film renders, so it is not here.

At a pinned governor tier, with the scroll position, canvas size, device pixel
ratio and MSAA count held equal, deferring the build leaves 20 per cent of pixels
differing by more than 8 of 255 and visibly drains the pane glass of its
environment lighting. The evidence:

- Injecting the scripts, giving them `defer`, or giving them `async` all produce
  the same 20 per cent. Keeping them parser-inserted and deferring only the
  first frame produces 0.002 per cent, which is film grain.
- The same build measured twice differs by 0 per cent, so the effect is
  deterministic, not sampling noise.
- The scene graph is byte-for-byte identical either way: every object's type,
  name, visibility, render order, position, scale, geometry vertex count and
  material properties match, as do `scene.environmentIntensity`, every pane's
  `envMapIntensity`, the camera, the pixel ratio, the tone mapping and the
  output colour space.
- Setting `envMapIntensity` to zero on both makes the two frames agree (0.066
  per cent). Regenerating the PMREM environment map late in both makes them agree
  (0.092 per cent). The differing input is the environment map itself: the PMREM
  built from `RoomEnvironment` comes out darker when it is generated after the
  document has been laid out than when it is generated during parsing.
- Warming the driver first, generating it twice, calling `gl.finish()` around it,
  and compiling the room's materials before generating all fail to recover it.

The mechanism is not understood. The rule is empirical, it held four ways, and it
is written next to both the script tags and the film's own start function. Anyone
who moves those tags should re-run the comparison.

**Chunking the first frame's shader compilation across frames.** With the build
deferred, compiling each object's program in 10 ms batches before the first
render cut the longest task from 1,963 ms to 697 ms. With the build back on the
parser, where it has to stay, it is worth nothing: median of three runs, 3,227 ms
of blocking time with it against 3,231 ms without, longest task 1,038 ms against
1,066 ms. It was written, measured, and removed rather than shipped for a gain
that is not there.

**Moving the film's script tags to the end of the body.** Pixel-identical, and
worse: first contentful paint 2,956 ms against 1,480 ms, blocking time 4,345 ms
against 3,231 ms, over three runs each.

## Still on the clock, and not this branch's to fix

- **The film's construction, 707 to 858 ms, parser-blocking, before first paint.**
  It cannot move without changing the render, as above. It is the floor on this
  page's first paint over a fast connection. Over a real network it is not the
  floor, because the scripts arrive after the header has painted: production's
  first contentful paint is 580 ms.
- **The first composed frame is still one task, now 1,027 ms.** It no longer
  blocks the paint, but a tap during it still waits. The only lever found for it
  was the chunked compile above, and it did not work in this configuration.
- **`site.js`, 275 ms, one long task, on every page.** `/pricing.html` pays the
  same 433 ms and is the fast page, so this is a whole-site item and not a
  homepage regression. Nothing else on the homepage crosses 50 ms: the fonts are
  base64 in the inline stylesheet and fetch nothing, `motion.js` and GSAP are not
  loaded here at all, and `pricing-config.js` does not appear in the profile.

## Reproducing this

```
node serve.js 3211            # this worktree
node serve.js 3213            # a worktree at the baseline commit
```

then the harness described at the top against `http://127.0.0.1:3211/`,
`http://127.0.0.1:3211/pricing.html` and the same two on 3213, with and without
`reducedMotion: "reduce"`, at CPU throttling 4x on a 412x823 profile. Take the
least contended of three and check the control moved by less than the thing you
are measuring. For the visual comparison, load both builds at `?tier=0` to pin
the adaptive governor, wait for `window.NV_SCENE` and then long enough for the
ignition and the damping to settle, screenshot at three scroll fractions, and
compare per-pixel; anything over about 0.1 per cent of pixels differing by more
than 8 of 255 is not grain.
